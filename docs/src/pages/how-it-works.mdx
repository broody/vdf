# How it works

## The flow

1. **Encrypt (instant).** The encryptor generates an RSA modulus N = p·q and
   derives the timelock key instantly:

   ```text
   y = x^(2^T mod φ(N)) mod N
   ```

   Because they know φ(N), the exponent `2^T mod φ(N)` is cheap. The message
   (e.g. a bid opening `(amount, salt)`, as felt252s) is encrypted with a
   Poseidon keystream under `key = poseidon('VDF_RSW_KEY_V1', ctx, |y|)`,
   where `|y| = min(y, N−y)` and `ctx` is an application context such as
   `H(auction, bid)`. There is no integrity tag: the application posts a
   commitment `poseidon(pt)` alongside the ciphertext. The factors p, q can
   then be **discarded** — nobody else ever needs them.

2. **Delay (sequential).** To decrypt, anyone must compute:

   ```text
   y = x^(2^T) mod N   — by T sequential squarings
   ```

   This is the "delay" of the VDF. It cannot be parallelized: each squaring
   depends on the previous one. The key materializes only at ~time T.

3. **Prove (short).** Once the squarings are done, the prover publishes a
   Wesolowski proof:

   ```text
   |y|  = min(y, N − y)                      sign-canonical output
   seed = poseidon(instance(N, x, |y|, T), nonce)
   L    = 251-bit candidate from seed        first nonce giving a prime
   q = floor(2^T / L),  r = 2^T mod L
   π = x^q mod N                             the proof
   ```

4. **Verify (O(log T)).** A verifier checks one equation:

   ```text
   π^L · x^r == ±|y|  (mod N)      in the signed group Z_N^*/{±1}
   ```

   Joint exponentiation shares the squarings across the two ~251-bit
   exponents. The challenge `L` is derived inside the verifier itself
   (in-program, from the instance and nonce) and must pass 20 Miller–Rabin
   rounds, so the prover cannot pick a favorable one — see
   *Concepts → Wesolowski VDF*. The same program then decrypts the
   ciphertext under the key from `|y|` and outputs
   `[instance_hash, ctx, poseidon(ct), poseidon(pt)]`; the application
   compares `poseidon(pt)` with the posted commitment.

## Why the encryptor isn't a trusted party

The RSW construction has **no trusted setup per message**: the encryptor is the
only party that ever knows the factors, and they can discard them immediately
after encryption. For sealed bids this is exactly right — the bidder keeps their
own bid secret from everyone, including the auctioneer, without any committee
or hardware trust.

## Why this beats the alternatives for reveal timing

| Mechanism | Standing decryptor? | Trust assumption |
|---|---|---|
| Operator reveal key (today) | Yes — operator decrypts anytime | Operator honesty |
| Threshold committee | No single member | M-of-N collusion + MPC over viewing key (unsolved) |
| TEE | No | Hardware + attestation |
| **RSW + Wesolowski VDF** | **No** | **Time itself (sequential work)** |
