# Cairo bigint

Cairo's native `felt252` is a field element — it has **no `PartialOrd`, no
`Rem`, no bit shifts, and `/` is field division**. You cannot do normal bigint
arithmetic on it directly. This repo uses a validated pattern:

## Representation

- **Limbs**: `u64`, little-endian.
- **Multiplication**: schoolbook columns accumulated in `felt252`, then split
  once into a u256's two u128 halves. For n contributing u64 products, the
  carry is below `n*2^64` and the column including carry is below `n*2^128`.
  Since Cairo's usize is u32, even the generic function stays below `2^160`,
  well below the field modulus; the next carry also fits u128. For the
  2048-bit configuration n is at most 33, so the tighter bound is `2^134`.
  Retain these bounds when changing limb widths. Only contributing pairs
  are visited; products are truncated only where the caller needs low limbs.
- **Carry**: after the split, `lo & 0xffffffffffffffff` → limb, `hi·2^64 + lo/2^64` → carry
  (constant-divisor division on u128 is integer division).
- **Subtraction with borrow**: compute in `u128`; the borrow applies to the
  **subtrahend**, not the minuend (a real bug caught by the Python model).
- **Bit scan in modpow**: `e % 2` / `e / 2` loop on u64 (not shifts);
  leading zero limbs/bits of the exponent are skipped.
- **Joint exponentiation**: `pi^L*x^r` scans both four-limb exponents from
  most significant bit to least significant bit, sharing each squaring. Reduce
  both bases, precompute `pi*x`, then choose the factor from `1`, pi, x, pi*x.
  Both zero exponents return one; the first nonzero factor is copied directly.
  The separate modpow remains for `2^T mod L`.

## Barrett reduction (HAC 14.42)

To reduce a 2k-limb product modulo a k-limb modulus N:

```text
mu = floor(b^(2k) / N)   computed offchain, k+1 limbs — VALIDATED in-program
                         (mu·N <= b^(2k) < (mu+1)·N; an unvalidated mu is an
                         attacker-controlled reduction)
q1 = p >> (k-1)
q2 = q1 * mu
q3 = q2 >> (k+1)
r  = p - q3*N   mod b^(k+1)      ← k+1 limbs, exact
while r >= N: r -= N             (at most 2 iterations)
```

The `k+1`-limb `r` is load-bearing: the quotient estimate undershoots by at
most 2, so `0 <= p − q3·N < 3N < b^(k+1)` and nothing wraps. Truncating `r`
to `k` limbs breaks reduction whenever `p − q3·N >= b^k` (e.g. `N = 2^512−1`,
`a = 2^448−1`, `b = 2^448+1` returns `p mod N − 1`). Rare for honest RSA
moduli — but in the RSW setting **N is chosen by the bidder**, so the
primitive must be correct for every modulus. Regression test:
`barrett_boundary_top_limb_all_ones`; sweeps: `scripts/hunt_barrett.py`.

q1 and q3 are span slices rather than array copies. The full q1*mu product
still computes its low columns: their carry contributes to the retained high
half. The k+1-limb normalization and both mu validations are unchanged.

## Measured execution cost

With Scarb/Cairo 2.18.0, dev profile, `stwo_no_ecop`, T=65536, joint
exponentiation, felt accumulation and span slices reduce the checked-in
512-bit vector from 14,838,481 to 5,629,093 steps (62.1%). The checked-in
2048-bit vector falls from 155,970,789 to 49,429,902 steps (68.3%). At 512
bits the independent savings are 41.3%, 33.2% and 2.3%; they are not additive.
These are execution-resource measurements; optimized proof generation and
onchain transaction gas have not been measured.

## Per-modulus limb domains

Each modulus gets its own limb count and Barrett constant:

| Modulus | Size | Limbs |
|---|---|---|
| N (RSA modulus) | 512-bit demo / 2048-bit production | 8 / 32 |
| L (Wesolowski challenge) | 251-bit + forced bit 192 | 4 |

Mixing domains breaks the reduction (an infinite normalize loop — the other
real bug the Python model caught).

## Validate before you port

`ref/cairo_model_v2.py` is the **exact Python mirror** of the Cairo algorithm.
Change it first, validate against the vectors, then port limb-for-limb. Never
port bigint changes blind.
